# FDE 기준 — fde-harness 의 개념적 헌장

> **이 문서의 역할**: fde-harness 가 *FDE 라고 정직하게 불릴 수 있는 조건* 을 정의합니다.
> **이 문서는 *개념* 만 박습니다.** 구현 (커맨드 이름·슬롯 이름·파일 경로·강제 메커니즘 세부) 은 spec 의 자유입니다. spec 은 본 문서에 비추어 평가될 뿐 본 문서가 prescribe 하지 않습니다.
>
> **이 문서가 먼저 작성된 이유**: 도구의 모든 결정은 *진짜 FDE 가 무엇인가* 에 닻을 내려야 합니다. 닻 없이 만든 도구는 이름과 실체가 어긋납니다.

## 0. 출처의 정직성

| 항목 | 사실 |
|------|------|
| **FDE 의 출처** | Palantir Technologies (2010년대) 의 직무 호칭 — Forward Deployed Engineer / FDSE |
| **공식 방법론인가** | **❌ 아닙니다.** Scrum 처럼 명명된 ceremony·artifact·role 체계가 없음 |
| **공식 핸드북** | 비공개. 공개된 건 채용 공고·CTO 발언·전 직원 회고록뿐 |
| **본 문서의 성격** | Palantir 의 *실천 패턴* 을 외부에서 관찰·재구성한 결과를 **fde-harness 내부의 표준** 으로 채택 |

→ "FDE 방법론" 이라는 표현 자체가 post-hoc 재구성. fde-harness 는 *자기의 FDE 해석* 을 명시적으로 박는다. 본 문서가 그 명시화다.

## 1. 3-Actor Model — Echo · Delta · AI

> **출처 정직성**: 3-Actor Model 은 FDE 원전(2-actor: Engineer + Operator) 의 *AI 시대 transpose* 다. AI 의 역할 정의는 본 도구의 변용이며 Palantir 원전과 무관하다.

### 1.1 역할 정의

| 역할 | 정체 | 차별점 |
|------|------|--------|
| **Echo (👤 Operator)** | 도메인 전문가, **코드 ❌**, workflow 의 실제 수행자 | "맞다/아니다" 의 권위. *말 자체* 가 spec 의 출처 |
| **Delta (👨‍💻 Engineer)** | **코드 ✓**, Operator 의 옆에서 그의 말을 코드로 옮김 | spec 작성·승인 통과·구현·검증·Ratchet 의 *책임 주체* |
| **AI (🤖 Assistant)** | Delta 의 인지 보조 | Delta 의 반복 작업·해석 부하 흡수. **Echo 와 직접 소통 ❌** |

### 1.2 잘못된 등치 (Ratchet 영역)

| 잘못된 등치 | 깨지는 것 |
|------------|---------|
| Echo = 개발자 (도구 사용자) | "도메인 전문가" 정의 무너짐 → 그냥 SDD |
| Delta = AI | 책임 주체 사라짐 → Operator 의 말을 *해석할 사람* 부재 |
| AI = Echo 의 대리 | AI 가 도메인 권위가 됨 → FDE 의 가장 큰 위반 |

→ **fde-harness 의 사용자 = Delta (Engineer)**. 도구는 Echo (Operator) 를 *반복적으로 환기* 시키지만, Echo 가 직접 도구를 사용하진 않는다. **Echo 의 발화·승인 흔적이 도구 안에서 추적 가능해야 한다 — 그 형식은 자유.**

### 1.3 책임 분리 (변경 불가 기준)

- **Echo 만이 할 수 있는 것**: 가치 정의 · 우선순위 · 수동 검증 · 도메인 권위
- **Delta 만이 할 수 있는 것**: Echo 의 발화를 *해석 없이* 옮기는 통역사 역할 · 기술적 가능성 제시 · 코드 책임
- **AI 가 할 수 *있는* 것**: Delta 의 인지 부하 흡수 (해석 제안·코드 초안·반복 검증)
- **AI 가 할 수 *없는* 것**: Echo 의 자리에 앉는 모든 행위 (가치 판단 · 우선순위 · 도메인 권위 · spec 의 본문 *생성*)

### 1.4 도구의 작동 모드 — 3 사이클 패턴

FDE 는 *기간* 에 따라 3가지 사이클 패턴이 있다 (Palantir 실천에서 관찰된 패턴 — 공식 명명은 아님). 각 모드는 같은 5가지 forcing function 을 *다른 강도* 로 강제한다.

| 모드 | 기간 | 핵심 성격 | F# 강도 프로파일 |
|------|------|----------|------------------|
| **스플릿 (Split)** | 며칠 ~ 2주 | 한 워크플로 한 조각, 매일 옆에. throwaway prototype 허용 | F1·F2·F3 최대, F4·F5 약 |
| **딥다이브 (Deep dive)** | 1 ~ 3개월 | 여러 워크플로 큐, 구조화된 사이클. 누적 학습 | 균형 (모든 F# 중간) |
| **챔피언 (Champion)** | 6개월 ~ 1년+ | 도메인 SME 됨, 멘토 transfer. graduation 준비 | F4·F5 최대, F1·F2·F3 약 |

**모드 전환 트리거**:
- 스플릿 → 딥다이브: 첫 demo 가 *진짜 통한다* 가 확인되어 더 깊이 가야 할 때
- 딥다이브 → 챔피언: 도구가 핵심 인프라가 되어 *고객측 champion* 을 형성해야 할 때
- 챔피언 → 종료: 고객측이 *자체 유지 가능* 해진 시점

**도구의 "모드 지원" 의미** (§ 5.2 의 모드 커버리지 입력):
- 해당 모드에 필요한 *최소 자산* (spec template · 사이클 의식 · transfer 메커니즘 등) 을 *어떤 형식이든* 제공
- 단순 *언급* 만으로는 충족 안 됨 — 자산 1개 이상 필요

**fde-harness 의 현재 모드 지원** (§ 5.2 평가용):
- 스플릿: ❌ (자산 없음)
- 딥다이브: ✅ (현재 기본 모드, 모든 사이클 자산)
- 챔피언: 🟡 부분 (`/fde-graduate` + `templates/graduation-template.md` — spec 009 부터)

→ 현재 모드 커버리지: **약 1.5/3** (딥다이브 ✓ + 챔피언 부분 0.5)

## 2. 5가지 Forcing Function — FDE 개념 코어

FDE 실천을 SDD·Agile·DevOps 와 구분짓는 5가지. fde-harness 는 이 5가지 각각에 대해 **"어떤 형식이든 강제하는가"** 로 평가된다.

각 forcing function 은 다음 3 부분으로 정의된다:
- **개념** — 무엇인지
- **본 도구가 강제해야 하는 것** — *형식은 자유*, 그러나 *효과* 는 반드시 보장
- **본 도구의 범위 밖** — 도구로 강제 불가능한 부분 (인정)

### F1. Co-location with Operator (운영자 옆에 있음)

**개념**: Engineer 는 Operator 의 컨텍스트를 *직접* 본다. 인터뷰(Operator 가 *말하는 것*) 와 관찰(Operator 가 *실제로 하는 것*) 은 다르며, 둘은 자주 어긋난다. FDE 는 후자에 닻을 내린다.

**본 도구가 강제해야 하는 것**:
- spec 의 본문은 *직접 관찰된 증거* 에 닻을 내려야 한다 — 기억·전언·추정만으로 작성된 spec 은 FDE 가 아니다
- *말* 과 *행동* 이 spec 안에서 구분되어야 한다
- 증거 없는 가정은 명시적으로 *가정* 으로 표시되어야 한다

**도구의 범위 밖**:
- 물리적 동좌석 — HR/물류 결정
- Engineer 가 본 것을 *진짜로 이해했는지* — 인지 영역
- Operator 의 *진짜 의도* 의 추론 — 본질적으로 불완전

### F2. Days-not-months Cycle (며칠 단위 사이클)

**개념**: 첫 movable demo 가 며칠 안에. perfectionism 거부. 속도 자체가 가치 — 빨라야 *피드백 횟수* 가 늘어 도메인 침투가 깊어진다.

**본 도구가 강제해야 하는 것**:
- spec 에는 *시간 한계* 가 있어야 한다 — 무기한 spec 은 FDE 가 아니다
- 시간 한계 초과 시 *가설 재확인* 의식이 강제되어야 한다 — stale 한 spec 을 모르고 진행하면 안 된다
- 사이클의 진척이 *시간 단위로 가시화* 되어야 한다 — 매일·매주 단위로 "지금 무엇이 열려있나" 확인 가능해야

**도구의 범위 밖**:
- 사용자의 가용 시간 — 본업이 따로 있는 메이커의 part-time 사용은 본 문서가 허용 (단 그 사실을 *명시* 해야 함)
- *진짜 demo-able* 인지의 판단 — Engineer 의 판단

### F3. Operator Ownership of Priority (운영자가 우선순위 결정)

**개념**: 다음에 무엇을 할지 PM 도 매니저도 CEO 도 아닌 *Operator* 가 정한다. Engineer 의 작성 순서·기술적 의존성·재미도가 아니다. **FIFO·LIFO·기술 우선 는 모두 FDE 의 반대**.

**본 도구가 강제해야 하는 것**:
- 다음 작업 선택의 *판단 근거* 가 가치 (Operator 단위) 와 시간 (deadline) 이어야 한다
- 선택 메커니즘이 *추적 가능* 해야 한다 — 왜 이 spec 이 선택됐는지 사후 검증 가능해야
- 우선순위 변경은 Operator 의 *발화* 에 근거해야 한다 — Engineer 의 임의 재정렬 ❌

**도구의 범위 밖**:
- *진짜 Operator* 인지의 검증 — 사회적 결정
- 가치 추정의 정확성 — Operator 의 도메인 이해

### F4. Operator's Language for Value (가치는 운영자의 언어로)

**개념**: 가치는 *Operator 의 단위* 로 측정. 분·결정·오류 건수·환자 수·고객 이탈률. Engineer 의 단위(LOC·story point·테스트 커버리지·엔드포인트 개수) 사용 시 *FDE 가 아니다*.

**본 도구가 강제해야 하는 것**:
- 가치 진술이 *Operator 의 정량 단위* 를 사용해야 한다 — 정성 수식어("개선됨", "더 빠름") 만 있으면 거부
- Engineer 단위는 *부수적* 으로만 허용되며 *가치* 로 인정되지 않는다
- 도구가 제공하는 모든 *예시·placeholder* 는 Operator 언어로 작성된다 (잘못된 단위가 *예시로도* 보이면 안 됨)

**도구의 범위 밖**:
- 단위의 *적절성* — Operator 의 도메인 이해 필요 (Engineer 가 검증 불가)
- 정량값의 *측정 정확성* — 실제 운영에서만 알 수 있음

### F5. Two-way Knowledge Flow (양방향 지식 흐름)

**개념**: Operator 가 Engineer 에게 도메인 가르치고, Engineer 가 Operator 에게 *소프트웨어 가능성* 가르침. **대칭**. 한쪽만 가르치면 FDE 가 아니라 컨설팅이거나 단순 외주.

**본 도구가 강제해야 하는 것**:
- 사이클마다 *양방향 학습* 이 수집되어야 한다 — Operator → Engineer (도메인) 와 Engineer → Operator (가능성) 두 방향
- 학습은 *영속화* 되어야 하며 *단방향* (단조 증가, 제거 금지) 으로 누적된다
- 음의 학습 (Ratchet 의 "절대 하지 말 것") 과 양의 학습 (검증된 패턴) 이 *둘 다* 수집되어야 한다 — 한쪽만 있는 비대칭은 FDE 의 위반

**도구의 범위 밖**:
- 학습의 *질* — 좋은 한 줄 규칙인지의 판단은 Engineer 의 책임
- *진짜로 가르쳐졌는지* — 영속화 ≠ 학습. 다음 사이클의 실제 적용 여부로만 검증됨

## 3. FDE 의 가치 사이클 — 가설 · 검증 · 측정

FDE 의 사이클은 SDD 의 `spec → impl → test` 가 아니라 **`가설 → 구현 검증 → 가치 측정`** 이다. 핵심 차이:

```
                        ┌──────────────┐
                        │  Operator    │
                        │  발화        │
                        └──────┬───────┘
                               ↓
              ┌────────────────────────────────────┐
              │  가설 형성                          │
              │  Operator 단위로 정량화             │
              └────────────────┬───────────────────┘
                               ↓
              ┌────────────────────────────────────┐
              │  Spec (계약)                       │
              │  What · Why · 가설 · Done means    │
              └────────────────┬───────────────────┘
                               ↓
              ┌────────────────────────────────────┐
              │  Plan + 승인 + 구현                 │
              └────────────────┬───────────────────┘
                               ↓
              ┌────────────────────────────────────┐
              │  Done means 통과                   │
              │  = 구현의 검증 (필요 조건)         │
              └────────────────┬───────────────────┘
                               ↓
                            [ 배포 ]
                               ↓
              ┌────────────────────────────────────┐
              │  Outcome 측정                      │
              │  = 가설의 검증 (충분 조건)         │
              │  → 사이클이 진짜로 닫힘             │
              └────────────────┬───────────────────┘
                               ↓
              ┌────────────────────────────────────┐
              │  다음 가설의 우선순위 조정          │
              │  (F3 의 입력)                      │
              └────────────────────────────────────┘
```

**핵심**:
- Done means 통과는 *구현* 의 검증이지 *가치* 의 검증이 아니다
- 가치 측정 없는 사이클은 *닫혀 보이지만 실은 열려 있다*
- 다음 가설의 우선순위는 *이전 측정 결과* 의 함수다 — 그래서 사이클이 진짜 연속됨

## 4. 인접 개념과의 정직한 구분

| 방식 | FDE 와의 핵심 차이 |
|------|-------------------|
| **SDD** (Spec-Driven Development) | Spec → 구현 → 검증. *가설·측정·Operator 언어·co-location·속도 없음*. fde-harness 가 F1-F5 의 *3개 이상* 을 강제하지 않으면 SDD 와 같다 |
| **Agile / Scrum** | sprint·story·velocity 의 Engineer 단위. FDE 와 거의 반대편 |
| **DevOps** | *인프라* 최적화. FDE 는 *워크플로* 최적화. 다른 추상화 층 |
| **컨설팅** | 조언함. FDE 는 *만듬* (코드 ownership 결정적) |
| **Solutions Engineering** | pre-sales 데모. FDE 는 post-sales + 코드 |
| **FAE** (Field Application Engineer, 1970s 반도체) | 표면적으로 유사한 직무 패턴. *직접 계승 관계* 는 본 헌장이 주장하지 않음 |

→ fde-harness 가 SDD 와 *진짜로 다르려면* F1-F5 중 **최소 3개 이상을 강제**해야 한다. 이게 본 문서의 가장 중요한 binding 조건이다.

## 5. fde-harness 의 명명 정직성 — 2-차원 등급

### 5.1 핵심 용어 정의

- **강제**: F1-F5 각각의 § 2 의 "본 도구가 강제해야 하는 것" bullet 의 *충족*
- **깊은 진척**: 해당 F# 의 **모든** bullet 충족
- **얕은 진척**: 해당 F# 의 **일부** bullet 충족 (1개 이상)
- **모드 커버리지** (§ 1.4): 도구가 지원하는 모드 수 / 3
  - 모드 자산이 *완전 부재* 면 0/3, 부분 자산은 *0.5* 로 계산 가능
  - **1/3**: 한 모드만 지원 / **2/3**: 두 모드 / **3/3**: 세 모드

### 5.2 2-차원 등급 매트릭스

fde-harness 의 README·플러그인 description 등에 사용 가능한 명명은 *F# 강도 (가로) × 모드 커버리지 (세로)* 두 차원으로 결정된다:

|                              | F# 강제 0~1       | F# 강제 2+ (얕은+깊은 합산)  | F# 깊은 진척 ≥ 3        |
|------------------------------|-------------------|-----------------------------|--------------------------|
| **모드 < 1.0 지원**          | 이름에서 FDE 제외 | FDE-inspired                | FDE proper (single-mode) |
| **모드 1.5~2.5 부분 지원**   | 이름에서 FDE 제외 | FDE-inspired (multi-mode)   | FDE proper               |
| **모드 3/3 완전 지원**       | 이름에서 FDE 제외 | FDE proper (limited)        | **FDE complete** ⭐       |

**4 단계 (높음 → 낮음)**:
1. **FDE complete** — 세 모드 모두 + F# 깊은 진척 3개+. *진짜 FDE methodology 구현*
2. **FDE proper** — F# 깊은 진척 3개+ (단일 모드 OK). *방법론 한 측면 정착*
3. **FDE-inspired** — F# 강제 2개+. *실천 차용*
4. **이름에서 FDE 제외** — F# 강제 ≤ 1. *FDE 라고 부를 정직성 부재*

**사용 가능 명명**:
- **FDE complete**: "complete FDE harness", "FDE methodology 의 모든 모드 지원"
- **FDE proper**: "FDE harness", "FDE methodology 구현 — 단일 모드 (딥다이브 등)"
- **FDE-inspired**: "FDE-inspired SDD harness", "FDE 실천 일부를 차용한 ..."
- **이름에서 FDE 제외**: "AI coding harness" 류 일반명

### 5.3 공통 조건 (모든 FDE 명명 등급의 필수)

- [ ] 3-Actor Model (§ 1) 의 책임 분리 정의가 도구 안에서 *명시* 됨
- [ ] 가치 사이클 (§ 3) 의 *측정* 단계가 도구 안에서 추적 가능 (Done means ≠ 가치 검증임이 명시)
- [ ] 본 문서가 README 에서 명시적으로 링크됨
- [ ] **도구가 지원하는 모드 (§ 1.4) 가 README·매니페스트에서 *명시*** ← spec 009 신규

### 5.4 정직성 원칙

- 자기 평가 결과 등급보다 *높은* 명명 사용 ❌ — 헌장의 binding 위반
- 자기 평가 결과 등급보다 *낮은* 명명 사용 ✓ — 항상 허용 (보수적 정직)
- 등급 *상승* 은 평가 결과 변경 시 즉시 가능
- 등급 *하강* 은 단방향 — 사용 패턴이 약화되어 미달해도 *이미 사용 중인 명명* 을 즉시 내리진 않으나, 다음 사이클 시작 시 재평가
- 평가 결과는 README 또는 별도 문서 (예: `docs/fde-self-evaluation.md`) 에서 *공개* — 외부 사용자가 "왜 이 등급인지" 확인 가능

## 6. 본 기준의 적용 규칙

### 6.1 모든 spec 의 self-check

새 spec 은 다음 질문에 *spec 본문 안에서* 답하지 않으면 머지하지 않는다.

1. 이 변경은 F1·F2·F3·F4·F5 중 *어느 것을* 진척시키는가? (정확히 어느 N개)
2. 진척이 *얕은가* (slot 추가만) *깊은가* (강제 메커니즘까지)?
3. 진척시키지 않는 forcing function 의 *미진척* 이 의식적인가 우연인가?
4. 3-Actor Model 의 책임 분리 (§ 1.3) 를 위반할 가능성이 있는가?

답이 "어느 것도 진척시키지 않음 + 미진척이 우연 + 위반 가능성 있음" 이면 spec 보류·재검토. 평가 양식은 **부록 A** 참조.

### 6.2 본 문서 자체의 갱신 규칙

본 문서는 fde-harness 의 *헌장* 이다. 변경 시:

- **별도 spec 필수** — `specs/{ID}-fde-criteria-revision.md`
- 변경 *사유* 가 외부 증거 (새 회고록·Palantir 공식 발화·실제 사용 경험·반례 발견) 에 근거
- *조건을 완화* 하는 변경은 fde-harness 의 명명 정직성을 약화시키므로 *별도 정당화* 필요
- 본 문서 (`docs/fde-criteria.md`) 가 본 기준의 SSoT — README · concepts.md · cycle-guide.md · spec 어디서든 본 문서로 *링크만* 한다

### 6.3 위반 발견 시

| 발견 시점 | 대응 |
|----------|------|
| **이미 머지된 변경에서** | 사후 회고 spec + Ratchet 규칙 (메타-FDE 자기일관성 회복 — 누적 회고 임계 도달 시 hard guard 화. *임계 수치는 `AGENTS.md` 의 Ratchet 규칙에서 정의 — 현재 2건*) |
| **진행 중 (review)** | `spec-revise` 분기 + 본 문서로 align |
| **본 문서 자체가 stale 한 것이 원인** | 본 문서 갱신 spec (§ 6.2) |

## 7. 미해결 질문 — 도구 강제의 한계

본 문서는 *어디까지 강제할 수 있는가* 의 경계를 정직히 인정한다.

### 7.1 영구적 한계 (도구 영역 밖)

- **Echo 의 정체성 검증**: 도구는 *지금 입력하는 사람이 진짜 Operator 인지* 모른다. Engineer 의 자기-서명·외부 ID 연동 등은 본 문서 범위 밖
- **AI 의 권한 한계**: AI 가 Operator 발화를 *해석* 하는 순간 F1·F4 가 흔들린다. "모든 AI 출력이 Engineer 의 *재서명* 을 거쳐야 한다" 는 원칙의 강제 강도는 미결정

### 7.2 결정된 항목 (이전 미해결 → 결정)

- **F2 의 weekly fallback 거부 (spec 007)**: 본업이 따로 있는 1인 메이커의 사용 패턴이 weekly 인 경우 — **weekly fallback 은 FDE 가 아니다**. fde-harness 가 weekly 사용 패턴이면 § 5 의 F2 강제 인정 불가. weekly 사용 자체는 막지 않으나, 정직성을 위해 *등급 한정* (FDE-inspired 이하) 필요.
- **본 도구의 기본 모드 = 딥다이브 (spec 009)**: fde-harness 는 *딥다이브 모드* 만 *기본 지원*. *스플릿 모드는 미지원* (자산 없음, 자산 추가 시 별도 spec). *챔피언 모드는 부분 지원* (graduation 자산 1개 — `/fde-graduate` + `templates/graduation-template.md` 부터). 다른 모드의 추가 자산 (예: `/fde-sprint`, `/fde-monthly-review`) 은 별도 spec 사이클의 대상.

### 7.3 미해결 — 데이터·사용 누적 후 결정

각 항목은 *해결 시까지 보수적 적용* 가이드를 함께 명시한다.

- **F1 의 관찰 증거 강제 범위 (B1)**: 작은 fix·docs 변경에도 적용되는가? → *보수적 적용: 미해결 동안은 새 **기능 spec** 에만 적용, fix/docs 는 예외*
- **F2 의 '며칠' 임계 수치 (B2)**: 3일? 7일? 14일? → *보수적 적용: **14일** 을 임시 한계로 가정, 사용 데이터 누적 시 조정*
- **F5 의 양방향 학습 빈도 (B6)**: 매 사이클 vs 누적? → *보수적 적용: **매 사이클** 묻되 "이번엔 없다" 답 허용*
- **가치 측정 시점 (B8)**: 즉시·1주·1개월·기타? → *보수적 적용: 시점 자유, outcome 기록 시 ***측정 시점*** 도 함께 명시*
- **F1 의 증거 임계 (강제 강도)**: 권고 vs hard guard? → 누적 회고 데이터 보고 결정 (헌장 § 6.3 의 임계 메커니즘 이용)

이 질문들은 미해결인 채로 *명시* 된다. 도구가 강제 못 하는 것을 강제하는 *척* 하는 게 본 기준의 가장 큰 위반이다.

## 부록 A: Spec 평가표 양식

본 기준에 따라 spec·변경을 평가할 때 사용. **형식은 자유**, 효과(F# 별 진척 판단)만 보장하면 된다.

```
변경: {간단한 제목}
spec: specs/{ID}

진척 평가:
  F1 (co-location)         ⬜ 진척 없음  ⬜ 얕은 진척  ⬜ 깊은 진척  ⬜ 의식적 보류
  F2 (속도)                 ⬜ 진척 없음  ⬜ 얕은 진척  ⬜ 깊은 진척  ⬜ 의식적 보류
  F3 (우선순위)             ⬜ 진척 없음  ⬜ 얕은 진척  ⬜ 깊은 진척  ⬜ 의식적 보류
  F4 (operator 언어)        ⬜ 진척 없음  ⬜ 얕은 진척  ⬜ 깊은 진척  ⬜ 의식적 보류
  F5 (양방향 학습)          ⬜ 진척 없음  ⬜ 얕은 진척  ⬜ 깊은 진척  ⬜ 의식적 보류

3-Actor Model 영향:
  ⬜ 책임 분리 위반 가능성 없음
  ⬜ 위반 가능성 있음 — 어떻게 완화? {설명}

의식적 보류 사유:
  {보류로 표시한 F# 들의 사유 — 다른 사이클로 미루는 명시적 근거}

집계: { 깊은 진척 N개 } + { 얕은 진척 M개 } + { 의식적 보류 K개 } + { 우연한 미진척 L개 }

판정:
  ⬜ 머지 가능 (3-Actor 위반 없음 + F# 중 깊은 진척 ≥1 OR 의식적 보류로 정직)
  ⬜ 강화 필요 (얕은 진척만 — 깊은 형태로 재작성)
  ⬜ 명명 재고 필요 (F1-F5 의 깊은 진척 누적이 3개 미만 → "FDE" 표현 한정)
  ⬜ 보류 (3-Actor 위반 가능성 + 완화 미정)
```
